# Paper PDFs that should stay out of search

You can make the portfolio searchable while asking search engines to exclude
the paper PDFs. However, **publicly accessible and unindexed is different from
private**: anyone with the URL can still download and redistribute the file.

## Why plain GitHub Pages is insufficient

For a PDF, Google documents this HTTP **response header**:

```http
X-Robots-Tag: noindex
```

It must be sent when fetching the **PDF itself**. Adding
`<meta name="robots" content="noindex">` to a web page only controls that HTML
page; it does not carry over to a linked or embedded PDF.

GitHub Pages does not offer custom response-header configuration. A `_headers`
file placed in this repository will not configure headers on GitHub Pages.
GitHub's own Pages response addresses this limitation in
[this discussion](https://github.com/orgs/community/discussions/84963).
Google describes PDF headers in its
[noindex documentation](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

Do not rely on `robots.txt` alone. A blocked URL can still appear in results,
and blocking crawling prevents the crawler from seeing a `noindex` header.
Keep the PDF crawlable so search engines can read that header. The same Google
documentation explains the distinction.

## Recommended setup: GitHub Pages site, separate PDF host

The site stays at `https://YOUR_USERNAME.github.io`. Upload only the PDFs to a
separate host with response-header support, then use absolute PDF links in
`index.html`. Cloudflare Pages supports an `_headers` file and direct uploads
without putting your PDFs in a public Git repository.

This is a suggested setup to perform yourself; no external account or deployment
has been created. The standard applies only to crawlers that honor `noindex`.

### 1. Prepare a local upload folder

Create this separately from your public website source, or use the ignored
`pdf-host/` folder here:

```text
pdf-host/
├── index.html
├── _headers
└── papers/
    ├── paper-one.pdf
    └── paper-two.pdf
```

Use a minimal `index.html` so the PDF host has a valid home page:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <meta name="robots" content="noindex">
    <title>Research documents</title>
  </head>
  <body><p>Research documents.</p></body>
</html>
```

Create a plain text file named exactly `_headers` (no extension):

```text
/*
  X-Robots-Tag: noindex
```

That rule covers every path on the separate PDF host, including the PDFs and
the host's root page. It does not affect your main GitHub Pages website.
It applies to static asset responses, not responses generated by Pages
Functions. This recipe uses only static files.
See [Cloudflare's header documentation](https://developers.cloudflare.com/pages/configuration/headers/).

### 2. Upload that folder to Cloudflare Pages

In a Cloudflare account, open **Workers & Pages**, create a **Pages** application,
and choose its **Direct Upload / drag and drop** option. Upload the contents of
`pdf-host/` with `_headers` and `index.html` at the deployment root; do not add an
extra outer folder level. Deploy and retain the production `*.pages.dev` URL.
See the current [Direct Upload guide](https://developers.cloudflare.com/pages/get-started/direct-upload/)
if the dashboard labels differ.

Use the production URL rather than a temporary preview deployment URL. Upload
the full folder again when updating documents. Cloudflare Pages has a 25 MiB
per-file limit for direct uploads; larger PDFs need compression or another host
that supports these headers. See the limits in the Direct Upload guide.

Do not also commit these PDFs to your public GitHub repository. That would
create additional publicly accessible copies outside the PDF host's header
configuration. The starter `.gitignore` excludes `pdf-host/` and
`assets/documents/papers/` to help keep those staging folders out of Git. Ignore
rules are not access controls and do not remove files already committed.

### 3. Verify the actual PDF response

Before adding the link to the website, substitute the real URL and run:

```sh
curl -I -L https://YOUR-PDF-HOST.pages.dev/papers/paper-one.pdf
```

The **final** response should be successful (`200`), have PDF content type, and
include a header equivalent to:

```http
content-type: application/pdf
x-robots-tag: noindex
```

If the final response lacks `noindex`, stop and fix the host configuration.
A header on a redirect alone does not cover the final PDF. Verify each PDF URL
you publish; check again after moving files or changing hosting. Do not add a
`robots.txt` rule that blocks access to these PDFs.

### 4. Link it from your Papers tab

Replace the relevant PDF placeholder span in `index.html`:

```html
<a href="https://YOUR-PDF-HOST.pages.dev/papers/paper-one.pdf">PDF</a>
```

This link remains public and easy for visitors to use. The header asks
cooperating search engines not to include that PDF URL in their results.
The title and summary you publish on your GitHub Pages site remain searchable.
Copies hosted on arXiv, conference sites, or other domains follow their own
indexing policies; this configuration does not affect those copies.

## If you require PDFs under the exact github.io domain

With plain GitHub Pages, you cannot configure the PDF response header at
`https://YOUR_USERNAME.github.io/papers/paper-one.pdf`. The separate host above
therefore changes the PDF's destination hostname. A custom domain with a
properly configured proxy / header-capable host is another possible setup,
but it is not part of this starter and does not retrofit headers onto the
original `github.io` URLs.

## If the document has already been indexed

After adding `noindex`, search engines need to recrawl the URL. Google notes
that this can take time and provides Search Console tools for URL inspection
and removal requests; see its
[noindex troubleshooting instructions](https://developers.google.com/search/docs/crawling-indexing/block-indexing#debugging).
Moving a PDF does not automatically remove old URLs or copies. If you need
access restrictions rather than search exclusion, use authentication or share
the document directly on request instead of publishing a public copy.
